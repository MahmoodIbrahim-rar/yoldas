# تشخيص حي لرفض حفظ وصفة الدليل

تمت مراجعة أول لقطتين من استعلام التشخيص الذي نفّذه المستخدم في Supabase بتاريخ 2026-08-25.

## حقائق مؤكدة من النتيجة

| الحقل الظاهر | النوع | قابلية القيمة الفارغة |
|---|---:|---|
| `calories` | `integer` | لا |
| `calories_estimate` | `integer` | نعم |
| `created_at` | `timestamp with time zone` | لا |
| `eaten_at` | `timestamp with time zone` | لا |
| `daily_log_id` | `uuid` | نعم |
| `fat_g` | `numeric` | نعم |
| `id` | `uuid` | لا |
| `log_date` | `date` | نعم |
| `meal_type` | `text` | نعم |

هذا يثبت أن جدول `meals` الحي أقدم وبنيته أوسع من النموذج البسيط الحالي. واجهة دليل الأكل كانت ترسل `calories_estimate` فقط، بينما الحقل `calories` ظاهر كحقل إلزامي، كما أن `eaten_at` إلزامي. هذا هو السبب المتوافق مع خطأ `400`: قاعدة البيانات ترفض صف الوجبة قبل حفظه عندما لا تصلها القيمتان الإلزاميتان.

تم تعديل الواجهة لإرسال `calories` و`eaten_at` عند وجود الجدول الحي القديم، ثم الرجوع تلقائيًا إلى البنية الأحدث أو الأبسط عندما لا تكون هذه الحقول موجودة. لا يلزم حذف الجدول أو تغيير بياناته القائمة.
